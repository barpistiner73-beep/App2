# FitPulse product requirements

## Training and exercise library

- Workout templates include a sticky, horizontally scrollable muscle-group filter and a search field that matches routine and exercise names. The weekly and single-session sections remain separate; empty sections are hidden while filtering.
- Workout cards prioritize one primary start action; edit, duplicate, sharing, and time-crunch start are grouped under a secondary disclosure. Up to three recently completed routines can be restarted from this browser's local history and are hidden during search/filtering.
- A new routine starts with an empty exercise list and an “Add exercise” action below it. Each row is defined independently by primary muscle group, primary-muscle subgroup, and preferred exercise, followed by editable set/repetition/load targets. Machine exercises are listed first when suitable, while the coach retains choice. Rows can be reordered or removed.
- Active workout sets are compact disclosure cards with exercise, set position, and optional set-type marker in the summary. Opening a set reveals its exercise selector, activation notes, animation, weight/reps, optional RIR, and one-tap set-type controls. Users can append a set using the previous set's load/reps; new sets open for immediate editing. Numeric fields have thumb-sized quick adjustments.
- Keep English exercise titles, separate weekly program splits from individual sessions, and provide search by name, muscle group, equipment, and unilateral/bilateral movement.
- Program builders can reorder exercises and keep the save action visible while scrolling. Duplicating a routine opens an independent editable copy; these controls are available from both trainee workout templates and the trainer demo builder.
- Workout category remains part of routine creation. Equipment availability is chosen at workout start, not in the routine builder; available equipment filters each routine row to its preferred exercise and trainer-approved equivalent exercises. Recovery goals choose an editable rest-time default (60, 90, or 180 seconds). The builder has no intensity or volume programming controls.
- Trainers manage preferred-to-equivalent exercise groups on the local “Equivalent exercises” page. Equivalence groups are explicitly selected by the trainer, and matching requires the same primary muscle and subgroup. These browser-local mappings are not synced to another user or device.
- The currently expanded live-workout set stays expanded through session re-renders, and frequently used session, set-type, and set-input controls have touch-friendly target heights.
- The local library covers chest, back, legs, shoulders, arms, core, and cardio, with barbell, dumbbell, cable, machine, bodyweight, Smith machine, and resistance-band variants. The same library powers trainee routine editing and the trainer demo builder.
- Every routine card (weekly, single-session, imported, or custom) can be edited. Each planned exercise stores its primary muscle group and subgroup; the exercise selected for logging may be its preferred exercise or a trainer-approved equivalent.
- Each exercise record includes ranked relative activation labels for primary and supporting muscles. These are heuristic educational estimates, not measured EMG data or individualized coaching.
- Personal routines carry workout category, recovery goal, exercise order, per-exercise primary muscle/subgroup, set and rep targets, initial weight, and one plan-level rest interval between sets. Logged sets capture the performed exercise, actual weight, reps, completion, and optional RIR. Workout and seven-day summaries count completed sets once under the planned primary muscle group only; supporting muscles do not receive fractional or secondary-set credit. Rest duration is a session-level interval between sets—not a property of each set. RIR 0 means technical failure; larger values estimate remaining technically sound repetitions.
- Time-Crunch Mode creates a round-robin set sequence across the program maker's muscle-group labels, with minimal transitions between different groups and at least two planned sets per represented muscle group where possible. Normal mode retains exercise-by-exercise order. One configurable rest interval sits between sets, with an in-session countdown; rest is not stored on individual set entries.
- Completing a set automatically starts the configured between-set rest countdown when another set follows. The timer remains manually available, and a zero-second rest setting does not start a countdown.
- After all sets for an exercise meet their target reps in the most recent logged exposure, the next session displays a progressive-overload suggestion of at least 2.5 kg or 5% of the prior load (whichever is larger, rounded to 0.5 kg). It is a suggestion, not an automatic load change or safety assessment.
- The 13 built-in workout cards use the specified Hebrew display labels and are divided between weekly splits and individual sessions. User-created/imported routines continue to use their supplied names.
- Exercise illustrations are original, lightweight animated SVG movement-path sketches. They are not Hevy assets, high-definition 3D human models, or validated form coaching. The accessible Hevy exercise page could not be inspected beyond its cookie notice; this implementation uses common exercise-card conventions (English name, equipment, target muscle, movement cue, and clear set logging), not a verified pixel-level replication.

## Routine sharing

- A share link embeds the complete routine definition (exercise IDs, order, sets, reps, starting weight, rest seconds, and optional RIR target) and can be imported on another browser with the local exercise catalog.
- Six-digit codes are stored only in the browser that created them. Codes do not resolve across devices or accounts. A link is the portable import mechanism; there is no hosted routine service.
- The trainer demo's “send to trainee” action records a local assignment and copies a share link. It does not deliver a program to a different person's account.

## Trainer demo and access boundary

- The trainer view includes a searchable sample roster, a target-versus-actual nutrition table, locally recorded workout feed/volume/set data, and a routine builder using the full exercise library.
- `#/admin/dashboard` is a client-side demo route. The `trainer_admin` profile role gates navigation and rendering, but browser localStorage and JavaScript are user-controlled and are not authentication or security-grade RBAC. The visible demo role switch is for local testing only.
- Only the `trainer_admin` profile role unlocks the local dashboard. The dashboard reports weekly compliance from the current browser's workout log against the existing five-workout weekly target and includes a row for this browser's nutrition totals; this is not per-client cloud monitoring.
- The roster contains static sample data. Only the current browser's logs are local records; there is no live feed, trainee account system, identity provider, server-side authorization, or cross-account synchronization. Do not use this implementation to protect real trainee data.
- Production deployment requires server-side identity verification (verified role or explicit allow-listed UID/email), authorization on every API request, persistent user/account data, and audited program delivery. A UI-only role check is insufficient.

## Nutrition and food logging

- Daily calorie, protein, carbohydrate, and fat targets are editable together on the dashboard and saved to the local profile. Calorie excess is highlighted red when intake exceeds the goal by more than 150 kcal. At or after 20:00 local time, show an evening notice when intake is at least 400 kcal below the goal; refresh while the page is open.
- The application’s primary visual palette is purple and black.
- Keep local reference nutrient values per 100 g; scale calories, macros, and tracked micros by logged grams. Search food names, categories, and tags with a 200 ms debounce.
- Search local foods immediately and, after the 200 ms input debounce, optionally search Open Food Facts for queries of at least three characters. Abort stale requests, show provenance, and let trainees add remote results only after selecting a food and portion.
- Barcode lookup uses Open Food Facts and records its source. Community-submitted values and missing nutrients must be identified; unknown nutrient values must not be presented as measured zeroes.
- Local branded/restaurant entries are estimates unless their record cites a verifiable label/manufacturer source. They are not asserted to be currently verified McDonald's, Domino's, Aroma, or Burgers menu values; restaurant recipes, regions, and portions vary. Use a scanned package label or verified manufacturer record for exact branded nutrition.
- The added McDonald's Israel and BBB calorie entries are estimates based on values supplied in the product request, not verified manufacturer data. Per-serving items use a serving-based amount; per-100 g items remain gram-based. Their macros and micronutrients are explicitly marked unavailable rather than filled with invented zeroes. They should not be described as verified values.
- Track calories, protein, carbohydrates, fat, fiber, sodium, total sugar, added sugar when available, potassium, omega-3, and omega-6. Show general adult FDA Daily Value references for sodium (2,300 mg), added sugars (50 g), potassium (4,700 mg), and fiber (28 g).
- Describe daily values as general references, not personalized medical advice. Explain that food-log omega ratios are estimates and are not medical or recovery targets.
- The displayed ratio is omega-6 divided by omega-3 (shown as `1:x`); 1:1 through 4:1 is highlighted in green, while ratios outside that requested display range are flagged. This display range is informational, not a medical recommendation.

## Data quality, privacy, and performance

- The Copilot coordination team has four assigned roles: Agent 1 (competitive intelligence/field research), Agent 2 (quality assurance/system audit), Agent 3 (core developer/integrator), and Agent 4 (trainee UX/innovation research). Each workstream hands findings to the developer; QA verifies fixes after implementation. These are coordinated assistant sessions, not autonomous processes embedded in the app or a continuously running production system.
- UX hypotheses from public sources: prioritize low-friction logging, editable defaults, fast exercise search, clear optional guidance, and user-controlled feedback. Evidence is directional: product-store pages describe vendor features, and available engagement studies focus mostly on general physical-activity apps rather than strength-training set entry. Competitive references reviewed include Hevy (https://play.google.com/store/apps/details?id=com.hevy), Strong (https://play.google.com/store/apps/details?id=io.strongapp.strong), JEFIT (https://www.jefit.com/), and MyFitnessPal (https://www.myfitnesspal.com/). Trainee engagement sources include Tobin et al. (2023, https://ijbnpa.biomedcentral.com/articles/10.1186/s12966-023-01447-9), Tong et al. (2022, https://pmc.ncbi.nlm.nih.gov/articles/PMC9309778/), Sae-Lee et al. (2023, https://formative.jmir.org/2023/1/e45298), and Baretta et al. (2019, https://www.jmir.org/2019/2/e11636).
- The local reference catalog is curated, not a live FDA/USDA database connection. FDC identifiers appear only on records with a verified match; restaurant estimates remain explicitly labeled as such. Open Food Facts search adds community records, not FDA-verified values.
- Logs, custom routines, demo role state, and trainer-demo assignments are stored in localStorage on the current browser. Camera scanning requires permission and HTTPS or localhost.
- Exercise search and filters operate on the local in-memory catalog, with no per-keystroke network requests. Animated SVGs use no large third-party exercise media.
- The current implementation does not bundle licensed 3D exercise media. Adding GIF/Lottie demonstrations requires appropriately licensed assets and per-exercise movement review.
